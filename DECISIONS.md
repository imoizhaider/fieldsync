# DECISIONS

Every assumption made while building, with the reason. Where the brief or the PRD was unclear, the option closest to the PRD was chosen.

## Backend

1. **Hosted Supabase project from `.env`** (option 1 of the backend selection rule). It was reachable and empty (no tables, buckets or users) when first probed, so applying the schema and seeding overwrote nothing. Docker is not installed on this machine, so option 2 was not available anyway.
2. **The keys are the new Supabase format** (`sb_publishable_…` and `sb_secret_…`). The publishable key is used wherever the brief says "anon key", the secret key wherever it says "service key". The secret scan looks for the exact service key value and for any `sb_secret_` string.
3. **Demo account password** is generated by `npm run seed` on its first run and stored in `.env.local` (git-ignored) as `SEED_PASSWORD`. It is not in the repository because anyone with the public key could otherwise sign in to the demo accounts.
4. **Seeded regions:** Region A (Researchers A and B can edit), Region B (only Researcher A; this is the region "not assigned" to Researcher B for gate G8), Region C (view only for both, as in the Regions design). The data lead has the role `lead` in all three.
5. **`npm run seed` wipes all data in the project** before every verify run, as the brief requires ("resets test data before every run"). This is called out in README and HANDOFF.

## Data model

6. **`region_members.role`** was added (`editor`, `viewer`, `lead`). The design shows "Can edit" and "View only" regions, which the PRD's two-column table cannot express.
7. **Record labels (SOIL-014)** need a number, but the id is a UUID. The device proposes the next number it knows for that region and type; the server keeps it if it is free and otherwise assigns the next free one. So a label can change once, on first sync, if two offline devices picked the same number. The UUID never changes.
8. **`records.field_meta`** stores, per field, the version, user, device and time of its last write. The merge function needs this to tell "another device changed this field since you last saw it" from "you changed it yourself twice".
9. **A title field** was added to the record form. The design's list shows titles ("Soil sample, north transect") but the form mock has no input for it. Empty titles fall back to "Soil sample", "Water sample" or "Wildlife sighting".
10. **Fields per type.** Soil: pH, moisture, temperature, depth (from the design). Water: pH, turbidity, temperature, dissolved oxygen. Wildlife: species, count. All types have title and notes. The record type cannot be changed after creation.
11. **GPS point and tracks share `gps_logs`** with a `kind` column (`point` for a record's location, `track` for a walk). Tracks belong to a region, not to a record.
12. **Extra server tables:** `profiles` (display names), `devices` (last sync per device, for the console's "Device sync" panel) and `applied_ops` (the idempotency ledger).
13. **Local tables are exactly the five in the PRD.** Regions, profiles, the conflict list and device list are small server caches stored as rows in `meta` rather than as new tables.
14. **One IndexedDB database per signed-in user** (`fieldsync-<user id>`), so two accounts on one device never mix and signing out loses nothing. Only the tiny "who is signed in" value is in localStorage, as the PRD allows.

## Sync and conflicts

15. **One write function, `sync_push(device, ops)`.** Clients have no insert, update or delete right on any table; Row Level Security only has read policies. `sync_pull(since)` is a second function but it only reads, and it runs with the caller's rights so Row Level Security applies.
16. **Idempotency by operation id.** Every outbox entry has a UUID. The server stores the result of each applied operation; a retry of the same id returns the stored result and changes nothing. This is in addition to device-made row ids.
17. **"Same field edited on two devices"** means: the field was written by a different device at a version newer than the version the pushing device last saw, and the values differ. Two edits from the same device never conflict with each other. Equal values are not a conflict.
18. **"Later" is the order in which the server receives the pushes.** The function never reads a device timestamp. Test T4 sets device B's clock a day back and B still wins.
19. **Edit against a deleted record:** each edited field becomes one `conflict_log` row of kind `edit_vs_delete`. "Restore record" (design) undeletes the record and applies those values, through `sync_push`. Editors and leads of the region can restore.
20. **Same-field conflicts stay "open" until a data lead presses "Mark reviewed"** in the console. The design shows open conflicts but no way to close one, so this small button was added.
21. **Rejected changes stay in the outbox** with status `rejected` and the server's reason. They are skipped by automatic sync until "Retry" is pressed. Later changes to the same record are held back with it, so one rejected record counts as one rejected change (as in the Sync rejected design).
22. **"A failed or interrupted push leaves the outbox untouched"** is taken literally: retry counters and backoff timers live in memory only. Only a definite server answer (applied or rejected) changes an outbox row.
23. **"Photo uploads resume"** means resume at photo granularity: each photo is its own outbox entry, finished photos are never sent again, and the interrupted one restarts. Photos are about 40 to 300 KB after compression, so chunked resumable upload (TUS) would add a dependency for no real gain. Uploads use `upsert`, so a photo that reached the server before the connection dropped is overwritten by the retry, not duplicated (this exact case is test T5).
24. **Pull cursor overlap.** `lastPulledAt` is set to the server time of the pull minus 5 seconds. Rows committed while a pull is reading are picked up by the next one; applying a row twice is harmless.
25. **Automatic sync triggers:** app open, the browser `online` event, 0.4 s after any local change while online, when the tab becomes visible, and a 20 second timer while the app is open. Backoff after a failure is 2, 4, 8 … up to 60 seconds and is reset by a reconnect or by "Sync now".
26. **Pending count in the status bar** counts records and tracks with waiting changes, not outbox rows (one record with three photos is "1 pending", as in the design).
27. **Deleting a record drops its photos that have not been uploaded yet.** They could never be shown again, so uploading them would waste the free tier.

## App

28. **No bundler for app code.** `src/` is served as plain ES modules. Only Dexie and supabase-js are bundled (with esbuild) into `dist/js/vendor/`. IBM Plex Sans comes from the `@fontsource` package and is copied into `dist/fonts/`.
29. **Hash routes** (`#/records`) so the app works under any sub-path and needs no server rewrite rules.
30. **The test server mounts the app at `/fieldsync/`**, so sub-path hosting is tested on every run.
31. **Photos are taken with `<input type="file" capture>`** rather than a live camera preview. It is the most reliable way to open the camera on phones, needs no camera permission prompt on most browsers, and still supports "Choose from library". The Permissions screen appears when the browser reports the camera as denied, or when location is denied.
32. **Badge text is "Pending"** as in the design. The PRD's wording "Pending sync" is the badge's tooltip and accessible title; test T1 checks both.
33. **The status bar is shown on every screen**, including the conflict log (whose mock omits it), because the layout rule says it is always visible.
34. **Stats and filter tabs stay visible while syncing.** The Syncing and All synced mocks omit them; hiding and showing them would make the list jump.
35. **The data lead lands on the review console**; researchers land on the record list. The role comes from `region_members`. The console collapses to one column on phone and tablet widths.
36. **Console extras** not in the mock: "Sign out" in the sidebar, "Mark reviewed" on conflicts, and Conflicts and Researchers views behind the sidebar links.
37. **Storage warning** appears at 80 % of the browser's storage estimate. "Free space" removes the local copy of photos that are already on the server; they are downloaded again when a record is opened online.
38. **A track being recorded is saved every 5 points.** If the app is closed mid-walk, the track is finished and queued the next time the Tracks screen opens.

## Tests

39. **Saved sessions for most tests.** A global setup signs the three accounts in once and stores each session as a Playwright storage state, to stay well inside Supabase's auth rate limits. Gate G7 and the FR-1 test sign in through the real screen.
40. **G7 "network fully off"** uses the browser's offline switch plus a route that aborts and records every request that still reaches the network. The test asserts that none of the app's own files had to.
41. **G11** uses a manifest and service worker check (the brief allows this instead of Lighthouse, whose PWA category was removed) plus Chrome's own `Page.getInstallabilityErrors`. Chrome always reports `in-incognito` inside a Playwright context, because test contexts are incognito profiles; that single environment error is filtered and any other error fails the gate.
42. **G12 "layout matches design"** cannot be asserted by a machine. The test asserts no horizontal scroll and 44 px targets on every screen at all three widths and writes screenshots to `artifacts/screens/`; these were compared by eye against `design/` while building.
43. **G10 has two halves:** `scripts/scan.mjs` scans `dist/`, and an end-to-end test asserts that the running app only makes requests to its own origin and the Supabase project.

## Fixes after the QA report (16 November 2026)

Each bug in `docs/QA_REPORT.md` was fixed at its root and proven by the QA case that failed before (log in `tests/qa/FIXES.md`). Choices made while fixing:

44. **I11, I13: the server never takes a region from the client for a row that exists.** A media op reads the region from the stored photo (the record id in the op is only used for a new photo); the delete itself is also filtered by that region. A GPS row may only link to a record of its own region; otherwise the op is rejected.
45. **I12: a device id belongs to the first user who pushes with it.** A push from another user with that id gets every op answered "rejected" (reason: "this device id is registered to another user"), instead of failing the whole call, so the app's normal "Sync rejected" screen explains it. The device row's owner never changes. The merge's "same device" test now also needs the same user, as a second guard. A device row whose id was taken over before this fix keeps its current owner; the seed resets the table anyway.
46. **G08: a delete carries the version it was based on.** The delete still wins (PRD line 94), but every field another device wrote after that version is logged as `edit_vs_delete`, with the overwritten value, so it can be restored from the conflict log. A delete with no base version (very old clients) counts as version 0, so all fields last written by another device are logged: more log rows, never a silent loss. On the deleting device the entry reads "Deleted on this device after it was edited on another one".
47. **B05, B06: validation in the form and again in `sync_push`.** Readings must be numbers. Only pH has a range (0 to 14, PRD and brief); moisture, temperature, depth, turbidity, oxygen and count must only be numbers because the PRD gives no range and negative temperatures are real. Empty stays allowed. The form shows "Not saved" with the reason and focuses the first bad field; nothing is written to IndexedDB. Records stored before the fix keep their values.
48. **F12: every request to the backend has a deadline** (30 s; 120 s for a photo upload or download), set once in the Supabase client's `fetch`. A timed-out request is a normal network failure: the outbox is untouched and the backoff retry continues. 30 s is longer than the slowest successful request seen on slow 3G in F10.
49. **E09: a start-up guard in `index.html`** (plain script, so it runs even when a module fails): one automatic reload, then a message with "Try again". The service worker now caches files one by one with up to 4 tries each, instead of one all-or-nothing `addAll`, but it still only activates with the complete file list, because a half-filled cache would open as a broken app offline.
50. **K09: the host badge is not hidden.** Netlify's free plan injects the "Powered by Netlify" badge and its script refuses to be dismissed on that plan. Hiding another party's element by id would be fragile and against the plan's terms. Instead the app measures anything fixed to the bottom edge that is not its own and keeps that strip free (`src/js/hostinset.js`), so no tab, button or sheet sits under the badge. With no badge (offline, another host) the strip is 0 px. Removing the badge itself is a manual choice (HANDOFF.md).
51. **K02: the console table scrolls inside its own box**; the page never gets wider than the screen.
52. **K06: sheets are real dialogs for the keyboard**: focus moves in (onto the safe button, "Keep record" or "Stay signed in"), Tab stays inside, Escape closes and focus returns. A "Skip to New record" link is the first Tab stop on the record list. Enter in a form field still does not save, on purpose: on a phone keyboard that would save half-filled forms.
53. **L04 (optional, done): CSV starts with a UTF-8 byte-order mark, and text cells that start with `=`, `+`, `-` or `@` get a leading apostrophe** so a spreadsheet shows them as text. Real numbers (for example -2.5) are written unchanged.
54. **E06 was checked with two real deploys** (`tests/qa/e06-redeploy.mjs`), because the QA case cannot swap a service worker inside the test browser. The second deploy carried a small real change: user text (titles, notes) uses `dir="auto"`, so Urdu shows right to left (finding from B08).
55. **Not changed:** the remaining findings in the QA report that are not counted as failures (D07 track saved every 5 points, Storage files of deleted photos, C04 multi-file pick, the A06 "Sign in again" button, F05 full lists on each pull, G03 `observed_at` from the device clock) are left for later; none loses data.
